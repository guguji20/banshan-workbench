# 商务 Agent 完整闭环任务总表

## 1. 范围锁定

本阶段只推进商务 Agent，不扩展创意中心、无限画布、分秒针反馈、摄影执行、服装道具、案例语义检索或其他业务板块。

系统定位为独立、完整的商务全流程系统，自身就是客户、项目、报价、合同、付款、验收、回款、文档和审计的唯一业务主数据源。当前不考虑销帮帮、飞书、外部回款表或其他第三方业务系统连接。

允许复用和补强的通用能力仅限商务闭环必需部分：Codex Tool Dispatch、Document Intelligence、Task、Asset、Approval、Artifact、Memory、权限、安装和发布。

### 开发方式：成熟开源优先

本阶段禁止把通用能力全部从零实现。当前已核验 129 个 GitHub 候选；选型、许可证、集成边界和四个先行 PoC 以 [BUSINESS_AGENT_OPEN_SOURCE_REUSE.md](./BUSINESS_AGENT_OPEN_SOURCE_REUSE.md) 为准。默认顺序为：

```text
Direct Dependency
→ Isolated Sidecar
→ Selective MIT/Apache Reuse
→ Design Reference Only
→ 最后才是自研
```

业务主数据、状态机、BSAIGC 协议、Codex Tool Dispatch、权限、审批、Evidence/Artifact adapter 仍由本项目掌握；解析、OCR、Office、聊天组件、表格、表单、规则、搜索和诊断优先复用成熟项目。

### 商务闭环起点

用户通过自然语言、拖入文件或选择已有项目发起工作：

```text
审一下这个合同。
把这个标书拆成必交清单。
按客户需求做一份报价。
合同已签，生成首款请款资料。
项目完成了，生成验收资料并更新回款计划。
把这个项目从报价到回款的状态、缺失资料和下一步待办整理给我。
```

### 商务闭环终点

```text
客户/商机建立
→ 需求和资料进入
→ AI 识别项目/客户/文档
→ 缺口追问
→ 合同审查或标书拆解
→ 人工确认
→ 统一项目主数据
→ 报价与审批
→ 合同与签署状态
→ 付款计划与请款
→ 交付里程碑与验收
→ 到账与回款跟进
→ 项目归档与经营复盘
→ Artifact / Audit / Memory
```

以下条件全部成立才算完整闭环：

1. 用户不需要在多个页面重复填写已经存在的信息；
2. 合同和标书结论能定位到原文页码、段落或表格；
3. AI 结果明确区分确定事实、规则命中、模型判断和待人工确认；
4. 报价、合同、请款、验收和回款共享同一 Business Workspace 主数据；
5. 每次生成文档冻结快照，历史文件不会被后续修改污染；
6. 客户、项目、金额、状态和文档变更必须留存版本、来源和操作审计；
7. 所有长任务可取消、恢复、重试、追踪和重放；
8. 所有输出先进入本地 Vault，只向 UI 返回 `assetId`；
9. 应用重启后项目、任务、审查结果、Approval 和 Artifact 不丢；
10. 有可安装的内部桌面版本和真实样本回归结果。

## 2. 不在本阶段内

- 创意中心和无限画布；
- 视频号案例智能搜索；
- 脚本贴图、平面、调色和音乐参考；
- 分秒针反馈和视频版本复盘；
- 摄影执行单扩展；
- 服装、道具库存；
- 正式 Web 端和云端多人协作；
- 未经人工审批的自动对外发送或自动提交；
- 销帮帮、飞书、外部回款表及其他第三方业务系统连接；
- 银行、税务、电子签章和客户门户直连。

## 6. 必须尽早提供的业务资料

代码可以先用匿名 fixture 开发，但要达到正式可用，以下资料不能拖到最后：

### 第 1 周需要

- 5-10 份匿名合同，最好包含已知问题；
- 2-3 份公司认可的合同模板或历史终稿；
- 公司关注的合同风险清单；
- 常见付款、验收、版权和违约处理原则；
- 2-3 份典型标书。

### 第 2 周需要

- 2-3 份报价 XLSX；
- 合同、请款、验收 DOCX；
- 公司主体、开票、银行和签章固定信息；
- 金额、税率、折扣和审批规则；
- 5 个完整历史项目样本。

### 内部台账定稿前需要

- 公司希望看到的客户、项目和经营统计字段；
- 项目阶段、合同状态、付款状态和归档状态定义；
- 市场负责人日常使用的筛选、待办和汇总口径；
- 备份、导出和历史项目迁移格式。

如果真实资料迟到，代码主线仍可推进，但合同规则准确度、模板还原和真实业务验收会顺延。

## 7. 验收数据集

正式 1.0 前至少建立：

- 20 份匿名合同；
- 5 份标书；
- 10 个完整商务项目；
- 3 类报价；
- 合同、请款、验收各 2 个模板版本；
- 付款正常、逾期、取消、部分到账等状态样本；
- DOCX、原生 PDF、扫描 PDF、复杂表格和损坏文件；
- 重复生成、并发修改、权限失败、磁盘异常、断网和重启恢复样本。

关键门禁：

1. 高风险 Finding 100% 带来源定位；
2. 金额、税率、日期和主体名称的确定性检查可重复；
3. 不确定结论必须显式标记；
4. 关键状态修改、正式文档生成和删除归档必须留有审批或审计；
5. 重复命令不会生成重复文档、重复付款记录或重复归档；
6. 重启后任务和审查结果可恢复；
7. 原始文件和生成结果始终先落本地 Vault；
8. UI 不持有密钥、本地绝对路径或业务权威。

## 8. 关键风险

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 公司合同规则不明确 | AI 只能做通用检查，无法符合公司风险偏好 | 第一周建立可版本化 Rule Pack |
| 合同样本太少 | 误报和漏报无法衡量 | 匿名化建立 20 份回归集 |
| 真实模板晚到 | 文档版式和字段映射顺延 | 先完成稳定 adapter，模板到位后替换 |
| 经营口径不统一 | 看板数据和回款状态无法被业务信任 | 第一周冻结阶段、金额、到账和归档口径 |
| 把模型判断当事实 | 审查结果不可靠 | 确定性检查、规则命中、模型判断分层 |
| UI 过早冻结 | 后续 Agent 工作流被页面结构绑死 | 先 PoC assistant-ui/React Admin 等成熟组件，只冻结协议和交互能力，不冻结最终视觉 |
| 开源项目只看 Star 不做真实 PoC | 解析、模板保真或 Runtime 边界失败后返工 | 第 1-3 日完成四个真实样本 PoC，并保留明确淘汰条件 |
| 许可证、模型权重或传递依赖污染 | 闭源安装包无法发布 | MIT/Apache 代码自动准入不代表模型自动准入；MPL/LGPL 人工审批；GPL/AGPL/非商业/研究限制默认阻断 |
| 范围再次扩散 | 商务闭环迟迟不能交付 | 本阶段禁止扩展其他板块 |
