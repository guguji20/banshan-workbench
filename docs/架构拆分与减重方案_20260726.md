# 半山商务工作台 · 架构拆分与减重方案

> 日期：2026-07-26
> 基线：`BSAIGC_DESKTOP` 1.3.0（以当日工作区文件为准）
> 性质：纯结构重构方案 —— **不改行为、不改协议语义、不改数据库 schema、不换技术栈**
> 目标读者：总控窗口 + 各开发车道

---

## 零、方案一句话

层间边界（UI → SDK → HostAdapter → IPC → Rust Host）已经很干净，不动；问题集中在**层内巨石文件**和**线性膨胀的 IPC 表面**。方案按 8 个批次做机械拆分 + 有限收敛：核心批次（P0–P5）约 **9–15 个专注工作日**，前后端两条车道并行时日历上约 **6–8 个工作日**；建议在 1.4（报价模板库 / 智能体 V2）动工**之前**完成 P1–P3，否则这三个文件还会继续变大，拆分成本逐轮上涨。

### 1.3 IPC 表面

70 个 tauri command、10 条事件通道、`HostAdapter` 接口 70+ 方法；每新增一个域要同步改 protocol.rs、lib.rs、DesktopHostAdapter、WebHostAdapter、BsaigcClient 五处。其中 `replay_*` 命令 10 个、`subscribe*` 方法 10 个，形状完全同构，是收敛空间最大的部分。

### 1.4 协议生成链（拆分兼容性已核实）

- ts-rs 采用**逐类型** `#[ts(export, export_to = …/src/generated/bsaigc/)]`，输出路径与类型所在模块无关 → **protocol.rs 拆成模块树不影响生成产物**。
- 唯一需要改动的一行：`scripts/generate-bsaigc-protocol.ps1` 的过滤器 `cargo test "protocol::export_bindings"`。ts-rs 的导出测试生成在**类型所在模块**内，拆分后测试名变为 `protocol::<子模块>::export_bindings_*`，子串过滤会漏配 → 改为 `cargo test export_bindings` 即可。脚本里的 required-bindings 清单校验不受影响。

## 二、总原则（每个批次都适用）

1. **只搬家，不装修**：拆分批次内禁止顺手改行为、改签名、修 bug；发现问题记录到清单，另开批次修。
2. **对外路径零变化**：Rust 侧靠 `mod.rs` 里 `pub use` 全量再导出，`crate::protocol::X`、`crate::business_workspace_service::BusinessWorkspaceService` 等调用点一个都不改；TS 侧 `client-sdk/index.ts` 的公开导出保持逐字节不变。
3. **一批 = 一个可独立回滚的提交**，遵守现有"开发窗口只改分配文件、总控统一审查提交"的纪律；拆分批次与功能开发**互斥占有**同一文件，不并行。
4. **每批出门先过门禁**：`pnpm verify`（含 protocol:generate、vitest、tsc、build、fmt、clippy、cargo test）；P1 额外要求 `src/generated/bsaigc/` 生成后 `git diff` 为空（零漂移证明）；前端批次额外跑一次桌面冒烟（一键验收）。
5. **上棘轮，防复发**：在 `pnpm verify` 中加一个 20 行的行数门禁脚本 —— 新文件上限（建议 Rust 1,200 行 / TS(X) 800 行），存量超标文件进白名单并记录当前行数，只许减不许增。没有这一条，两个版本后会长回来。

## 三、批次方案

### P0 基线与护栏（0.5 天）

- 干净工作树上打 tag（如 `pre-split-1.3.0`），完整跑一次 `pnpm verify` 记录耗时基线。
- 加入行数棘轮脚本 + 白名单（现状即初值）。
- 明确本轮冻结窗口：P3 进行期间，business_workspace_service.rs 不接任何功能改动。

### P1 protocol.rs → `protocol/` 模块树（0.5–1 天）

目标结构（14 个文件，每个 150–500 行）：

```text
src-tauri/src/protocol/
  mod.rs                 # 版本常量、通道常量、兼容函数、pub use 全量再导出
  common.rs              # OperationContext / CommandReceipt / DomainEvent / HostError / HostStatus / Approval …（约 20 类型）
  project.rs             # 约 7 类型
  task.rs                # 约 10 类型
  asset_backup.rs        # Asset + Backup + Storage，约 28 类型
  brain.rs               # Brain/Codex，约 14 类型
  auth.rs                # 约 11 类型
  ai_credential.rs       # 约 13 类型
  case.rs                # 约 10 类型
  execution_brief.rs     # 约 10 类型
  requirement_brief.rs   # 约 14 类型
  business_workspace.rs  # 约 76 类型（含全部 Business* payload；后续可再二分）
  contract_review.rs     # 约 36 类型（含 Document/Evidence/Finding/Rule）
  desktop_settings.rs    # 约 6 类型
  diagnostic_memory.rs   # Diagnostic + Memory + Module，约 10 类型
```

要点：类型连同其手写 impl（约 23 个，如 `Display for HostError`）一起搬；`mod tests` 里 3 个契约测试搬进 `mod.rs`；同批修改生成脚本过滤器（见 1.4）。

**验收**：verify 全绿 + 生成目录 diff 为空 + 全仓无调用点改动（`git diff` 只含 protocol 目录与脚本一行）。

### P2 client-sdk 拆分（1–1.5 天）

- `BsaigcClient.ts`（3,268 行 / 156 方法）拆为：`client/core.ts`（start/stop、事件订阅与缺口重放、快照组装、错误归一）+ `client/commands/{project,task,asset,brain,auth,case,briefs,business,contractReview,backup,settings}.ts`。
- 模式：各域文件导出**接收 ctx（adapter + 内部状态访问器）的纯函数**，`BsaigcClient` 类保留原方法名做一行委托 → 组件层零改动，`index.ts` 零 diff。
- 131KB 的 `BsaigcClient.test.ts` 按同样的域切成对应测试文件。

**验收**：`pnpm test`/`check` 全绿；`index.ts` 无 diff；组件目录零改动。

### P3 business_workspace_service.rs → `business_workspace/`（3–5 天，本方案核心）

目标结构（利用 Rust 允许同一类型多个 inherent impl 块分布在不同模块）：

```text
src-tauri/src/business_workspace/
  mod.rs             # Service 结构体、execute_command 总分发、list/replay、pub use
  schema.rs          # migrate / ensure_table_column / 各历史迁移
  events.rs          # append/load/replay、Receipt、command_fingerprint、审计列
  validate.rs        # normalize_* / validate_* / 金额与时间校验（约 40 个纯函数）
  financial.rs       # derive_financial_summary、effective_contract_amount 等
  customers.rs       # 客户（3 fn）+ assign
  quotes.rs          # 报价行项、确认（6 fn）
  documents.rs       # 单据创建/状态机/快照冻结（31 fn，必要时再分出 generate.rs）
  delivery.rs        # 里程碑/交付版本/发送/签收
  payments.rs        # 付款计划与请款（19 fn）
  invoices.rs        # 发票开具/红冲/附件
  receipts.rs        # 到账/回款/冲销（19 fn）
  archive.rs         # 归档快照/完整性/导出（12 fn）
  prefill.rs         # 历史预填（12 fn）
  profile.rs         # 供方资料（6 fn）
  requirement_sync.rs
  tests/             # 约 5,150 行测试按聚合切成对应文件
```

子批次顺序（每个子批独立绿灯，单批风险可控）：

1. 先把 `mod tests` 原样搬到 `business_workspace/tests.rs`（visibility 调成 `pub(crate)`），全绿 —— 0.5 天；
2. 抽基建：schema / events / validate / financial —— 1 天；
3. 聚合两两一组搬家：documents+quotes → payments+invoices+receipts → delivery+archive+prefill+profile+customers —— 1.5–2.5 天；
4. tests.rs 按聚合二次切分，收尾清理 —— 0.5–1 天。

**验收**：每子批 `cargo test business_workspace` 绿；收尾全量 verify 绿；`lib.rs` 只改一行 `mod` 声明。

### P4 第二波后端拆分（核心 1–1.5 天；可选 +1.5–2 天）

- **必做**：contract_review_service.rs（4,419 行）→ `contract_review/{mod,sessions,findings,evidence,reports,promote}.rs`。理由：路线图里"标书拆解"要复用这条管线，立项前拆完。
- **可选**（视痛感排期，模式同上）：asset_service.rs、business_tool_registry.rs（76 个工具定义拆成按域的 defs 文件）、r2_backup.rs、ai_credential_service.rs、business_closure_service.rs。这批不阻塞任何路线图项，可放到 P7 之后零散消化。

### P5 前端拆分（2.5–4 天）

**App.tsx（3,063 行 → 目标 <800 行）**，1–1.5 天：

- App 保留壳 + 装配；把各中心的状态与回调抽成 `src/app/` 下的域 hooks：`useProjectsState`、`useBusinessState`、`useContractReviewState`、`useBrainState`、`useSettingsState`…
- `mapR2Backup / mapDesktopUpdate / localizeHostError / timestampToIso` 等纯函数移到 `src/app/mappers.ts`、`hostErrorText.ts`。

**BusinessDocumentsCenter.tsx（4,583 行 + 105KB CSS → 每文件 <800 行）**，1.5–2.5 天：

```text
src/components/business-documents/
  index.tsx            # BusinessDocumentsCenter 壳与视图路由
  OverviewView.tsx  CustomerView.tsx  DocumentsView.tsx
  DeliveryView.tsx  FinanceView.tsx   PaymentsView.tsx  ArchiveView.tsx
  shared.tsx           # Field / Metric / InlineNotice / VaultFilePicker / CenterEmpty …
  labels.ts            # 全部 *_LABELS / 状态文案 / 图标映射
  money.ts             # cents/percent/millis 换算（含现有单测）
  drafts.ts            # 15+ 个 draft 构造器与 to-input 转换
  guards.ts            # *BlockReason / allowedDocumentTransitions 系列
  styles/              # CSS 按 View 切分 + base
```

现有 `BusinessDocumentsCenter.test.ts` 跟随 helpers 落到 labels/money/drafts/guards 的测试文件。SettingsCenter、BusinessWorkbench、DesktopShell 进观察名单，本轮不动。

**验收**：test/check/build 绿 + 桌面冒烟走一遍七个视图。

### P6 IPC 表面收敛（可选，1.5–2.5 天）

- **推荐范围**：只统一同构的重放与订阅 —— `replay_*` 10 个命令合并为 1 个 `replay_domain_events { domain, afterSequence, limit }`；10 条事件通道合并为 1 条带 domain 标签的通道（SDK 内按 domain 映射回强类型，类型安全保留在生成层）。净效果：约 20 个命令/方法、8 条通道消失，五处同步改动变三处，WebHostAdapter 占位维护量减半。桌面应用前后端同包发布，无兼容窗口负担：同一提交内切换并删除旧命令。
- **不推荐**：把 `execute_*` 也泛化成单命令。各域 CommandEnvelope 本就是强类型汇聚点，泛化只省少量样板，却把类型错误从编译期推到运行期，不划算。

### P7 死代码与体积治理（1–2 天 + 一个决策）

路线图 1.2.3 已列"死代码清理"，此处给执行口径：

1. 逐个摘掉 `#[allow(dead_code)]`，用编译警告生成"真死"清单；按 AGENTS.md 规则，共享底座（Task/Asset/Memory/Security/Client SDK/Codex Host）依赖审计通过后才删，删不动的转 cargo feature（默认关闭）。
2. **决策项 —— media-runtime（约 134MB DLL + ffmpeg）**：媒体生成属冻结范围；审计确认商务闭环（含合同解析、OCR——OCR 走的是 Windows `Media_Ocr`，不是 ffmpeg）无引用后，从 `tauri.conf.json` 的 bundle resources 中移除 → 安装包显著缩小；将来创意中心解冻改为按需下载。
3. codex 运行时（341MB）是核心依赖，保留；仓库传输继续按 UPSTREAM_CODEX.md 走 LFS/release-artifact，不变。

### 4.1 分批工期（专注工作日，按当前 Agent 辅助开发模式估）

| 批次 | 内容 | 工期 | 前置 |
| --- | --- | ---: | --- |

| P1 | protocol 模块树 | 0.5–1 | P0 |
| P2 | client-sdk 拆分 | 1–1.5 | P0（与 P1 无依赖） |
| P3 | business_workspace 拆分 | 3–5 | P1 |
| P4 核心 | contract_review 拆分 | 1–1.5 | P1 |
| P5 | App.tsx + 单据中心拆分 | 2.5–4 | P2 |
| **核心小计（P0–P5）** | | **9–15** | |
| P6（可选） | replay/订阅收敛 | 1.5–2.5 | P1–P3 后 |
| P7 | 死代码 + 体积 | 1–2 | 可独立穿插 |

| **全部** | | **13–20** | |

### 4.2 两条车道并行（符合现有多窗口分工模式，文件天然互斥）

```text
车道 A（后端）：P0 → P1 → P3 → P4核心        ≈ 5.5–8 天
车道 B（前端）：P2 → P5                       ≈ 3.5–5.5 天
```

并行时**核心批次日历约 6–8 个工作日**；P6/P7 视情况再加 2–4 天。单人串行则按 4.1 合计（约 2–3 周）。

### 4.3 与产品路线的穿插建议

- **窗口一（现在，1.3.x 修复期）**：P0+P1+P2，约 2–3.5 天。protocol 与 client 是所有新功能都要过手的文件，先拆收益立现。
- **窗口二（1.4 立项前，硬前置）**：P3 + P4 核心。理由：报价模板库要动"协议 + 存储"，智能体 V2 要动 host 层，标书拆解要复用审查管线——三者恰好都砸在这几个最大的文件上。先拆后建，否则 12,348 行会继续往 15,000 走。
- **窗口三**：P5 前端拆分，可与窗口二并行；P6、P7 结尾收。

### 4.4 完成判据（做完的定义）

- 全仓最大源文件 <1,500 行（Rust）/ <1,000 行（TSX），棘轮脚本在 verify 中生效；
- `pnpm verify` 耗时不高于基线（增量编译应更快）；
- P1 生成产物零漂移、P2 `index.ts` 零 diff、全程无行为改动提交；
- 冒烟：七个单据视图 + 合同审查 + 报价生成 + 归档导出各走一遍。

## 五、风险与对策

| 风险 | 对策 |
| --- | --- |
| 拆分批次与功能开发撞文件 | 批次占有制：P3 期间冻结 workspace service 的功能改动；按车道排期错开 |
| 生成脚本过滤器漏改导致 TS 漂移 | P1 验收含"生成后 diff 为空"硬门禁；过滤器改 `export_bindings` |
| 测试搬家后偷偷变红/变少 | 每子批对比 `cargo test`/vitest 用例计数，只许持平或增加 |
| git blame 历史变难追 | 接受成本；用 `git log --follow` / `blame -C -M`；一批一提交便于二分定位 |
| 拆完又长回来 | 行数棘轮 + 新文件上限写进 verify，白名单只减不增 |
| 顺手重构冲动（改命名/改逻辑） | 原则 1 写进批次说明；review 时看到行为 diff 直接打回 |

## 六、明确不做的事

不换状态管理库（SDK 投影模式工作良好）；不改 SQLite schema 与迁移；不动 WebHostAdapter 的定位（仍是协议占位 + 契约测试）；不做 `execute_*` 全泛化；不在本方案内引入新依赖；不做大爆炸式一次性重写。

---

*本方案的行数、函数分布、类型分组均来自 2026-07-26 对工作区文件的静态统计；执行前如有大的合入，重跑一遍统计校准子批次即可，结构结论不受影响。*
